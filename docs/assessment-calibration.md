## なぜ測るのか

期待範囲を推測で決めると、モデルの正常な揺れを回帰と誤判定するか、
逆に本当の劣化を見逃す。範囲は必ず実測から決める。

## 測り方

```bash
python3 server/scripts/extract-golden.py            # Swift の定義から設問と本文を取り出す
cd server
node --experimental-strip-types scripts/measure-golden.mjs scripts/golden-candidates.json 5
```

第4引数に基準ID（`rubric-writing-a` 等）を渡すと、その級だけを測る。

設問と本文は `Kentei/Domain/DemoAssessment.swift` を唯一の出所とし、
測定用 JSON はそこから生成する。2箇所で持つと必ずずれる。

`ANTHROPIC_API_KEY` は `server/.env.local` から読む。値は出力しない。

## 範囲の決め方

1. 同じ提出を3〜5回採点し、最小と最大を記録する
2. 実測の外側に余裕を足して範囲を決める
3. **範囲全体が合格ラインの片側に収まることを必ず確認する**

3 を外すと、点数は範囲内なのに合否だけ外れる状態が生まれ、
回帰なのか揺れなのか区別できなくなる。
この検査は `GoldenAnswerRegressionTests.testExpectedRangesDoNotStraddleThePassingLine`
で機械的に行っている。

## 設問を伴わない測定は本番と条件が違う

採点サーバーは当初、本文だけを受け取っていた。
「課題への対応」の観点があるのに設問を渡していなかったため、
その観点は実質採点できていなかった。

設問を渡すようにした前後で、同じ本文の点が次のように変わった。

| 提出 | 設問なし | 設問あり | 説明 |
|---|---|---|---|
| a-no-argument（事実の羅列） | 0.500〜0.550 | **0.250〜0.338** | 設問に答えていないことが検出されるようになった |
| golden-rich（B級・仕事の説明） | 1.000 | 1.000 | 設問に合致しているため変化なし |
| golden-strong（B級） | 0.700〜0.875 | **0.300〜0.750** | 設問と噛み合わず、揺れが大きくなった |

基準回答は**必ず設問とともに測る**。設問から切り離すと、
何に対する解答なのか分からないまま範囲だけが残る。

## 較正で判明したこと

### 中間帯の基準回答は作りにくい

合格ライン付近を狙った提出は、同じ文章でも測定のたびに合否が反転する。

| 提出 | 実測 | 判定 |
|---|---|---|
| B級・短い3文の答案（設問なし） | 0.550〜0.675 | 合否が反転。使えない |
| A級・中位を狙った答案（設問なし） | 0.688〜0.838 | 合否が反転。使えない |

基準回答は判定の境界から離して置く。境界付近の挙動を見たい場合は、
基準回答ではなく別の手段（実利用のログ等）で追う。

なお A級の `a-adequate` は、設問を添えたことで 0.888 に収束し安定した。
設問がないと採点がぶれること自体が、境界付近の不安定さの一因だった。

### 旧版の期待範囲は実測とずれていた

`golden-2026-08-v2` の2件は、実測すると範囲を外れた。
推測で置いた範囲がそのまま残っていたためで、較正で初めて分かった。

### 注入ケースに正当な解答を混ぜてはいけない

指示文と正当な解答を混ぜた提出は 0.375〜0.575 と幅が広く、合格ラインに近づいた。
指示に従ったのか解答が良かったのかを切り分けられないため、指示文だけで構成する。

API上限や認証エラーは発生時点で確認し、過去の上限解除日を作業停止の条件にしない。

## 再較正が必要になるとき

- 採点モデルを変えたとき（`server/src/scoring.ts` の `MODEL_ID`）
- 採点プロンプトを変えたとき
- ルーブリックの観点・重み・合格ラインを変えたとき
- **設問の文言を変えたとき**（基準回答は設問への解答として測っているため）

いずれの場合も、測り直してから期待範囲を更新し、
`GoldenAnswerSuite.version` を上げる。
